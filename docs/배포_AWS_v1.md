# AWS 배포 (8단계) — 결정·근거·절차

컨테이너로 만든 서비스를 인터넷에서 접속 가능한 주소로 올리는 단계.
이 문서 하나로 "왜 이렇게 정했는지"와 "무엇을 어떤 순서로 하는지"를 모두 볼 수 있게 썼다.

명령은 Windows CMD(내 PC)와 bash(서버) 두 가지가 섞인다. 각 단계에 어디서 치는 것인지 표시했다.

## 2. 배경 — 배포가 무엇을 요구하는가

결정을 이해하려면 이 서비스가 가진 제약 네 가지를 먼저 봐야 한다.

첫째, 데이터가 디스크에 남아야 한다. 시도 기록은 SQLite 파일(`data/app.db`)에, 녹음 원본은
`data/uploads/`에 쌓인다. 기록 화면과 통계, 나중의 ML 재학습이 전부 여기에 의존한다.
컨테이너는 지우면 안이 사라지는 물건이라, 이 폴더만은 컨테이너 바깥에 두고 연결해 써야 한다.
그 연결 장치를 볼륨이라고 부른다.

둘째, 브라우저 마이크는 HTTPS에서만 열린다. 보안 규칙상 안전한 연결이 아니면 브라우저가
마이크 접근을 막는다. 예외는 `localhost` 하나뿐이라 로컬 테스트는 HTTP로 됐지만,
외부 주소는 반드시 인증서가 필요하다. 인증서가 없으면 서비스의 핵심 기능이 아예 동작하지 않는다.

셋째, 계산이 CPU에서 돈다. 음성 인식(Whisper)이 요청 하나에 수 초를 쓴다.
GPU를 쓰면 빠르지만 시간당 비용이 몇 배라, 개인 프로젝트에서는 CPU로 두고 그 대신
"얼마나 걸리는지"를 정확히 재는 것이 9단계의 목표다.

넷째, 트래픽이 사실상 없다. 나와 몇 명이 쓰는 데모다. 확장성보다 비용과 절차의 단순함이 중요하다.

## 3. 결정과 근거

### 3-1. EC2를 고른 이유

세 가지 후보를 놓고 비교했다.

| | App Runner | ECS Fargate | EC2 |
|---|---|---|---|
| 성격 | 컨테이너를 올리면 알아서 굴려주는 완전 관리형 | 서버 없이 컨테이너만 띄우는 관리형 | 가상 서버 한 대를 빌려 직접 운영 |
| 영속 볼륨 | 붙일 수 없음 | EFS(네트워크 디스크)만 가능 | EBS 디스크를 그대로 사용 |
| HTTPS | 기본 제공 | 로드밸런서 + 인증서 서비스 필요 | 직접 구성 |
| 고정비 | 중간 | 높음 (로드밸런서 상시 과금) | 낮음 |
| 재현 절차 | 짧다 | 길다 | 중간 |

App Runner를 버린 이유는 볼륨이다. 디스크를 붙일 방법이 없어서 재배포나 재시작 때마다
`app.db`와 녹음이 사라진다. 기록이 쌓이는 게 이 서비스 기능의 절반이라 이건 타협할 수 없다.

Fargate는 EFS라는 네트워크 디스크를 붙일 수는 있다. 다만 SQLite는 파일 잠금으로 동시 접근을
막는 방식인데, 네트워크 파일시스템에서는 그 잠금이 설계대로 동작하지 않는 경우가 있어
DB 파일이 깨질 위험이 있다. 여기에 로드밸런서 상시 비용까지 더해진다.
트래픽이 없는 데모에 매달 고정비를 내면서 위험까지 안을 이유가 없다.

EC2를 고른 결정적 이유는 "오늘 검증한 것을 그대로 옮길 수 있다"는 점이다.
로컬에서 통과한 `-v sorisaegim-data:/app/data` 구성이 서버에서도 똑같이 동작한다.
새로 배울 것도, 새로 검증할 것도 최소가 된다. 관리형이 아니라 보안 업데이트나 재시작을
직접 챙겨야 하지만, 그건 리눅스마스터·AWS SAA 준비와 겹치는 학습이라 손해가 아니다.

바꿀 조건: 사용자가 늘어 여러 대로 나눠야 하거나, SQLite를 PostgreSQL 같은 DB 서비스로
옮기게 되면 그때는 Fargate가 유리해진다. 지금은 아니다.

### 3-2. t3.medium (2 vCPU · 4GiB)

한 단계 아래인 t3.small은 메모리가 2GiB다. torch와 Whisper small을 올리면 1.5~2GB를 쓰므로
아슬아슬하고, 메모리가 모자라면 리눅스가 프로세스를 강제 종료한다.
그렇게 되면 "느린 것"이 아니라 "가끔 죽는 것"이 되어, 9단계에서 재려는 응답시간과 오류율이
전부 오염된다. 측정이 목적인 단계에서 측정 환경이 불안정한 것은 본말전도다.

그래서 여유 있는 쪽에서 시작하고, 실측한 뒤 낮추는 순서로 간다.
반대 순서(작게 시작해 문제가 나면 올리기)는 원인이 성능인지 메모리인지 구분하는 데
시간을 더 쓰게 된다.

### 3-3. 서울 리전 (ap-northeast-2)

응답시간을 재는 것이 9단계 목표인데, 해외 리전에 두면 측정값에 국제 구간 지연이 섞인다.
그러면 "우리 코드가 느린 것"과 "거리가 먼 것"을 구분할 수 없다.
사용자도 나도 국내에 있으니 서울이 맞다.

### 3-4. Ubuntu 24.04 LTS

Amazon Linux 2023도 후보였지만, 도커 컴포즈 플러그인 설치 절차가 버전마다 달라
스크립트가 길고 깨지기 쉽다. Ubuntu는 도커 공식 저장소 절차가 그대로 통한다.
게다가 컨테이너 베이스 이미지가 Debian 계열(`python:3.13-slim`)이라 호스트와 계열이 같아,
문제가 났을 때 같은 명령으로 확인할 수 있다.

### 3-5. Caddy를 앞에 두는 구조

앱을 인터넷에 직접 노출하지 않고 앞에 Caddy라는 웹서버를 세운다. 구조는 이렇다.

```
브라우저 ──HTTPS(443)──▶ Caddy ──HTTP(8000, 내부망)──▶ 소리새김 앱
```

이렇게 하는 이유는 세 가지다.

- 인증서를 Caddy가 자동으로 발급받고 만료 전에 갱신한다. 손이 가지 않는다
- 앱 코드는 HTTPS를 몰라도 된다. 지금 코드를 한 줄도 고치지 않고 배포할 수 있다
- 외부에 열리는 포트가 80·443 둘뿐이 된다. 앱의 8000번은 서버 안에서만 보인다

인증서 발급 방식은 HTTP-01을 쓴다. 도메인이 이 서버를 가리키고 80번이 열려 있으면
발급 기관이 그것으로 소유를 확인해준다. 처음에는 DNS 방식을 생각했는데, 그 방식은
DuckDNS용 플러그인을 넣은 Caddy를 직접 빌드해야 해서 관리 대상이 하나 늘어난다.
HTTP-01이면 공식 이미지를 그대로 쓸 수 있다.

### 3-6. 자동 기동은 `restart: unless-stopped`로

서버가 재부팅돼도 서비스가 저절로 살아나야 한다. systemd 서비스 파일을 따로 만드는 방법도
있지만, 도커에 이미 재시작 정책이 있다. 도커 데몬이 부팅 때 올라오면서 컨테이너를 다시 띄운다.
관리할 파일이 하나 줄고, 로컬과 서버의 동작이 같아진다.

`unless-stopped`는 "내가 명시적으로 멈춘 게 아니면 다시 띄운다"는 뜻이다.
점검하려고 일부러 내린 컨테이너를 재부팅이 멋대로 살리지는 않는다.

### 3-7. 서버에 비밀번호를 두지 않는다 (IAM 역할)

ECR에서 이미지를 받으려면 인증이 필요하다. 액세스 키를 서버 파일에 적어두는 방법이 흔하지만,
서버가 뚫리면 그 키로 계정 전체를 건드릴 수 있다.
대신 인스턴스에 역할을 붙이면 AWS가 임시 자격증명을 자동으로 넣어준다.
파일에 남는 비밀이 없고, 권한도 "ECR 읽기"만 준다. 서버가 털려도 이미지를 덮어쓸 수는 없다.

### 3-8. 고정 IP(탄력적 IP)

EC2는 재시작하면 공인 IP가 바뀐다. IP가 바뀌면 도메인이 엉뚱한 곳을 가리키고,
그 상태로는 인증서 갱신도 실패한다. 그래서 고정 IP를 할당해 붙인다.
월 몇 천원이 들지만, 주소가 흔들리면 디버깅에 그보다 훨씬 비싼 시간이 든다.

## 4. 파일 구성 — 무엇이 왜 있나

| 파일 | 역할 | 왜 필요한가 |
|---|---|---|
| `deploy/compose.prod.yaml` | 서버에서 앱 + Caddy 두 컨테이너를 띄우는 정의 | 로컬용 `compose.yaml`과 달리 이미지를 빌드하지 않고 ECR에서 받는다. 앱 포트를 밖으로 열지 않는다 |
| `deploy/Caddyfile` | Caddy 설정 | 도메인·인증서 이메일·프록시 대상·업로드 상한·접근 로그 |
| `deploy/.env.example` | 환경변수 서식 | 이미지 주소·도메인·이메일은 사람마다 다르니 파일로 분리. 실제 `.env`는 커밋하지 않는다 |
| `deploy/user-data.sh` | 인스턴스 첫 부팅 시 실행할 설치 스크립트 | 도커·컴포즈·AWS CLI 설치와 저장소 클론까지 자동화. 수동 설치 단계를 없애 재현성을 높인다 |

로컬 `compose.yaml`을 서버에서 그대로 쓰지 않는 이유는, 로컬은 소스에서 빌드하고
서버는 완성된 이미지를 받는 구조라 시작점이 다르기 때문이다. 억지로 한 파일에 합치면
조건 분기가 생겨 둘 다 읽기 어려워진다.

## 5. 절차

### 0. 계정 준비 (제일 먼저)

1. AWS 계정 생성 후 루트 계정에 MFA 설정
2. Billing → Budgets에서 월 예산과 알림을 건다.
   금액이 확정되지 않았어도 일단 켜는 것이 요점이다. 요금 사고는 알림이 없어서 커진다
3. 콘솔 우상단 리전을 ap-northeast-2(서울)로 고정

### 1. ECR 리포지토리와 이미지 업로드 (내 PC, CMD)

ECR은 AWS가 제공하는 비공개 이미지 보관소다. 만든 이미지를 여기 올려두면 서버가 받아간다.

```
aws ecr create-repository --repository-name sorisaegim --region ap-northeast-2
aws sts get-caller-identity --query Account --output text
```

두 번째 명령이 계정 ID를 알려준다. 아래 `<계정ID>` 자리에 넣는다.

```
aws ecr get-login-password --region ap-northeast-2 | docker login --username AWS --password-stdin <계정ID>.dkr.ecr.ap-northeast-2.amazonaws.com

docker tag sorisaegim:dev <계정ID>.dkr.ecr.ap-northeast-2.amazonaws.com/sorisaegim:latest
docker tag sorisaegim:dev <계정ID>.dkr.ecr.ap-northeast-2.amazonaws.com/sorisaegim:2026-08-15
docker push <계정ID>.dkr.ecr.ap-northeast-2.amazonaws.com/sorisaegim:latest
docker push <계정ID>.dkr.ecr.ap-northeast-2.amazonaws.com/sorisaegim:2026-08-15
```

날짜 태그를 같이 올리는 이유는 되돌리기 위해서다. `latest`만 있으면 새 이미지가 문제를
일으켰을 때 돌아갈 지점이 없다. 날짜 태그가 있으면 `.env` 한 줄만 바꿔 이전 버전으로 되돌린다.

이 단계가 절차 전체에서 가장 오래 걸린다. 이미지가 5GB대라 가정용 인터넷 업로드 속도로는
30분 이상 걸릴 수 있다. 당일에는 이 명령을 맨 먼저 걸어두고, 기다리는 동안 2~4단계를 진행한다.

### 2. IAM 역할 만들기 (콘솔)

1. IAM → 역할 → 역할 생성 → 신뢰할 수 있는 개체 유형: AWS 서비스 → 사용 사례: EC2
2. 권한 정책에서 `AmazonEC2ContainerRegistryReadOnly` 하나만 선택
3. 역할 이름 `sorisaegim-ec2-role`로 저장

### 3. 인스턴스 생성 (콘솔)

| 항목 | 값 |
|---|---|
| AMI | Ubuntu Server 24.04 LTS (x86_64) |
| 인스턴스 유형 | t3.medium |
| 키 페어 | 새로 만들어 `.pem` 파일을 안전하게 보관 (분실하면 접속 불가) |
| 스토리지 | gp3 30GB |
| IAM 인스턴스 프로파일 | `sorisaegim-ec2-role` |
| 고급 세부정보 → 사용자 데이터 | `deploy/user-data.sh` 내용 붙여넣기 |

디스크 30GB인 이유는 이미지 5GB에 도커 내부 캐시와 누적 녹음까지 감안한 값이다.
8GB짜리 기본값으로 두면 이미지를 받다가 꽉 찬다.

보안그룹(방화벽) 규칙

| 포트 | 허용 대상 | 용도 |
|---|---|---|
| 22 | 내 IP만 | SSH 접속 |
| 80 | 전체 | 인증서 발급 확인, HTTPS로 리다이렉트 |
| 443 | 전체 | 실제 서비스 |

22번을 전체에 열면 전 세계에서 로그인 시도가 들어온다. 내 IP만 허용한다.
8000번은 어디에도 열지 않는다 — Caddy를 거치지 않는 우회 경로를 만들지 않기 위해서다.

### 4. 고정 IP와 도메인 연결 (콘솔 + DNS)

1. EC2 → 탄력적 IP → 할당 → 인스턴스에 연결
2. 도메인의 A 레코드를 그 IP로 지정
   - 보유 도메인이 있으면 해당 DNS 관리 화면에서 추가
   - 없으면 DuckDNS에서 무료 서브도메인을 만들고 IP를 등록 (5분이면 된다)
3. `nslookup <도메인>` 으로 IP가 제대로 나오는지 확인

3번을 건너뛰지 않는 것이 중요하다. DNS가 퍼지기 전에 Caddy를 띄우면 인증서 발급이 실패하고,
실패를 반복하면 발급 기관의 시도 횟수 제한에 걸려 몇 시간을 기다려야 한다.

### 5. 기동 (서버, bash)

```bash
ssh -i <키>.pem ubuntu@<도메인>

cd ~/sorisaegim
git pull
cd deploy
cp .env.example .env
nano .env        # APP_IMAGE · SITE_ADDRESS · TLS_EMAIL 채우기

aws ecr get-login-password --region ap-northeast-2 \
  | docker login --username AWS --password-stdin <계정ID>.dkr.ecr.ap-northeast-2.amazonaws.com

docker compose -f compose.prod.yaml up -d
docker compose -f compose.prod.yaml ps
docker compose -f compose.prod.yaml logs -f caddy
```

마지막 명령으로 인증서 발급 로그를 지켜본다. 성공하면 `certificate obtained successfully`
비슷한 줄이 나온다. 실패하면 원인이 대개 DNS나 80번 포트다.

### 6. 검증

순서대로 확인하고, 각 결과를 기록한다.

1. `https://<도메인>` 접속 — 주소창 자물쇠 확인
2. 문장 선택 → 듣기 → 녹음 → 채점. 마이크 권한 창이 뜨면 HTTPS가 제대로 붙은 것이다
3. 기록 화면에 시도가 남는지
4. `docker compose -f compose.prod.yaml restart` 후에도 기록이 남는지 (볼륨 확인)
5. 인스턴스를 재부팅한 뒤 저절로 살아나는지 (재시작 정책 확인)
6. 첫 요청과 이후 요청의 소요 시간을 각각 적어둔다

6번이 9단계의 출발점이다. 로컬 기준선은 콜드 4.61초 / 웜 1.74초인데 그건 16 vCPU 환경이었다.
t3.medium은 2 vCPU라 더 느릴 것이고, 그 차이를 아는 것이 측정의 시작이다.

### 7. 문제가 생기면

- 컨테이너만 이상하면: `docker compose -f compose.prod.yaml down` 후 다시 `up -d`
- 새 이미지가 문제면: `.env`의 `APP_IMAGE`를 이전 날짜 태그로 바꾸고 다시 `up -d`
- 인증서 발급이 계속 실패하면: 재시도를 반복하지 말고 DNS와 80번 포트부터 확인한다.
  반복 실패는 발급 한도에 걸린다
- 디스크가 찼으면: `docker system prune -a` 로 안 쓰는 이미지 정리
