## 3. 먼저 풀어야 할 것 3건

착수 전에 이 셋을 확인한다. 특히 3-1은 이후 일정 전체를 좌우한다.

### 3-1. 미세조정 모델 웨이트가 로컬에 없다 (블로커)

`stt/phone.py`가 `data/models/w2v2-jamo/`를 찾는데 그 폴더가 없다.
따라서 `available()`이 False이고 `/attempts?engine=phone`은 503을 낸다.
이 프로젝트의 대표 성과(오탐 52%→6%) 경로가 현재 로컬에서 재현 불가라는 뜻이다.

`data/`는 통째로 gitignore이므로 저장소를 clone해도 웨이트는 따라오지 않는다.
Colab 학습 산출물(`OUTPUT_DIR`)이 드라이브에 남아 있는지 먼저 확인한다.
없으면 재학습부터라 일정이 통째로 밀린다.

배치·export 절차는 `docs/colab_실행가이드.md` Step 9.

배치 방식은 아래 셋 중 하나를 골라 `docs/log.md`에 이유와 함께 남긴다.

| 방식 | 장점 | 단점 |
|---|---|---|
| 이미지에 굽기 | 기동 즉시 사용 가능, 외부 의존 없음 | 이미지 3GB대, 코드 한 줄 고쳐도 전량 재푸시 |
| 볼륨 마운트 | 이미지 가벼움 | 배포 대상 서버마다 수동 배치 필요, 재현성 낮음 |
| 비공개 원격 저장소에서 받기 | 이미지 가볍고 재현 가능 | 최초 기동 시 다운로드 시간, 토큰 관리 필요 |

권장은 세 번째다. `stt/phone.py`가 이미 `PHONE_MODEL_DIR` 환경변수로 경로를 덮어쓸 수 있어
코드 변경이 거의 없고, AI Hub 원본과 달리 파인튜닝된 웨이트는 비공개 보관이면 재배포 제약에 걸리지 않는다.

### 3-2. `requirements.txt`에 버전 핀이 하나도 없다

과거에 venv 재생성 후 기능이 깨진 전례가 있다(수동 설치분 미기록).
컨테이너는 매번 새 환경을 만드는 구조라 핀이 없으면 같은 문제가 반복된다.

`pip freeze`를 통째로 박지 않는다 — Windows 로컬에서만 딸려온 것이 섞여 리눅스 컨테이너에서 깨진다.
2단으로 나눈다.

- `requirements.txt` — 직접 의존만 `==`로 고정 (위 2절의 실측 버전 사용)
- `requirements.lock.txt` — `pip freeze` 전체 스냅샷. "그때 무엇이 깔려 있었나"의 근거용

`torch`는 지금 `requirements.txt`에 없다. whisper·transformers가 끌어오는 전이 의존이라
버전이 운에 맡겨져 있다. 명시적으로 고정하고 CPU 휠 인덱스를 함께 지정한다.

```
--extra-index-url https://download.pytorch.org/whl/cpu
torch==2.12.1
```

GPU 휠이 잡히면 이미지가 몇 GB 불어나 이미지 용량·로딩 시간 측정이 무의미해진다.

### 3-3. 네이티브 의존성의 리눅스 절차가 없다

`g2pK`·`konlpy`는 JVM과 mecab 네이티브를 요구한다.
현재 문서화된 절차는 Windows 전용이다 — MSVC C++ 워크로드 + `C:\mecab`의 mecab-ko-msvc +
`libmecab.dll`을 site-packages에 복사 (`experiments/README.md`).
이 절차는 컨테이너에서 그대로 못 쓴다. 리눅스에서 필요한 시스템 패키지 목록을 뽑아야 하고,
그 목록이 곧 Dockerfile의 `apt-get install` 줄이 된다.

참고로 `CLAUDE.md`가 언급하는 `setup_venv.cmd`가 저장소 루트에 없다.
문서만 남고 파일이 유실됐는지 확인이 필요하다.

### 7단계 — 실행환경 컨테이너화 (~2026-08-09)

1. 기준 상태 확정 — `git pull`, 테스트 통과 확인, venv Python 버전 확인(3.13.7 → 베이스 이미지 `python:3.13-slim`)
2. 의존성 고정 — 3-2대로 2단 구성
3. 로컬 실행 재현 — `pytest` 전량 통과, 서버 기동 후 녹음→채점 1회, `/attempts`를 기본 엔진과 `engine=phone` 각각 1회.
   각 단계 소요 시간을 초 단위로 기록한다. 특히 모델 최초 로딩 시간 — 이후 콜드스타트 판단의 기준선이 된다
4. Dockerfile 초안 — 단일 스테이지부터. 최적화는 나중에
5. 로컬 이미지 빌드 성공까지. 실패 로그는 버리지 말고 정리해 둔다(네이티브 의존성 목록이 여기서 나온다)
6. 컨테이너 실행 + SQLite 볼륨 연결. 재시작 후 데이터가 남는지 확인
7. 모델 파일 배치 방식 확정(3-1) 후 반영
8. 이미지 용량·모델 로딩 시간 측정, 줄일 지점 목록화

### 8단계 — 클라우드 배포 (~2026-08-21)

1. 계정·리전 설정, 요금 알림 먼저 건다
2. 배포 방식 결정 — 비용과 CPU 추론 특성 기준으로 하나 고르고 이유를 결정 이력에 남긴다.
   이 서비스는 요청당 수 초 CPU 추론에 상시 트래픽이 없다. 콜드스타트에 모델 로딩이 얹히는 점이 판단의 핵심이다
3. 인스턴스·보안그룹·포트 설정, 접속 확인
4. 레지스트리에 이미지 푸시 → 서버에서 pull·실행
5. 외부 접속 1차 확인, 도메인·HTTPS 적용 여부 결정
6. 외부 URL에서 전체 플로우(녹음→STT→채점→결과) 실행 확인
7. 컨테이너 자동 기동 설정(재시작 정책 또는 systemd)
8. 로그 수집 위치 정리, 오류 응답 처리 점검
9. 실사용 점검 — 업로드 용량 제한, 타임아웃, TTS 캐시 동작
10. 배포 절차를 명령 순서대로 문서화 (완료 기준 "재현 가능")

브라우저 마이크는 보안 컨텍스트를 요구하므로 HTTPS가 사실상 필수다.
5번을 "나중에"로 미루면 6번이 통째로 막힌다.

## 6. 지켜야 할 것

`CLAUDE.md`에 있는 것 중 이 단계에서 특히 걸리는 항목만 추린다.

- `data/`는 통째로 gitignore다. AI Hub 데이터와 그 재포장 산출물은 재배포 금지 — 이미지에 굽지 않는다.
  컨테이너 빌드 컨텍스트에 `data/`가 딸려 들어가지 않도록 `.dockerignore`를 함께 만든다
- `attempts.audio_path`는 프로젝트 루트 기준 상대경로다. 컨테이너 경로가 달라져도 절대경로로 되돌리지 않는다
- 비교는 항상 발음형 공간에서 한다. 모델 출력처럼 이미 발음형이면 `recognized_is_phonetic=True`
- 골드셋(1주차 녹음 20건 = attempts 1~20)은 테스트 전용, 학습 금지
- 지표는 측정 조건과 한계를 함께 적는다
